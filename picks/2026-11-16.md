# Building effective agents

**Who:** Erik Schluntz and Barry Zhang, Anthropic (the page credits "Erik S. and Barry Zhang")
**What / when:** blog post, December 19, 2024, Anthropic Engineering
**Full piece:** https://www.anthropic.com/research/building-effective-agents
**Jump in here:** https://www.anthropic.com/research/building-effective-agents#appendix-2-prompt-engineering-your-tools (Appendix 2, "Prompt engineering your tools", ~8 short paragraphs and two lists, ~3 min)

## Why this one

A widely shared, practical post on how to build LLM agents, written from Anthropic's work with customers. Its main message ("find the simplest solution possible") is a nice counterweight to framework-heavy agent hype. The appendix is the most hands-on part: it treats tool definitions as an interface for the model, like a UI for a human, and ends with a concrete small story about file paths. Fits Martin's audience of Python learners well, since "write a clear docstring" turns out to be agent advice too. Current era after Friday's ResNet paper, blog format (last five were paper, podcast, essay, video, paper), and new people.

## What's said there

> "While building our agent for SWE-bench, we actually spent more time optimizing our tools than the overall prompt. For example, we found that the model would make mistakes with tools using relative filepaths after the agent had moved out of the root directory. To fix this, we changed the tool to always require absolute filepaths—and we found that the model used this method flawlessly." (Appendix 2, last paragraph, text verified: yes, fetched 2026-11-16; note the original em dash if quoting the last sentence)

> "One rule of thumb is to think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good agent-computer interfaces (ACI)." (Appendix 2, text verified: yes)

> "Think of this as writing a great docstring for a junior developer on your team." (Appendix 2, text verified: yes)

- Some formats are much harder for an LLM to write than others, even if they're equivalent to a program: a diff needs the number of changed lines in its header before the code is written, and code inside JSON needs escaped newlines and quotes.
- Suggestions: give the model tokens to "think" first, keep formats close to what appears naturally on the internet, avoid overhead like counting thousands of lines or string-escaping.
- "Put yourself in the model's shoes": if a tool's use isn't obvious from its description, it probably isn't for the model either. Test with many inputs and "Poka-yoke your tools" (change arguments so mistakes are harder).
- The SWE-bench story: relative paths broke after the agent changed directories, so they required absolute paths and the errors went away.

**B, educator's angle, medium:**

There's a short appendix in Anthropic's "Building effective agents" post (2024, by Erik Schluntz and Barry Zhang) that reads a lot like advice for writing code for other people.

Their suggestion is to put as much effort into the interface between an agent and its tools as people put into interfaces for humans. Describe each tool so it's obvious how to use it, and in their words, "Think of this as writing a great docstring for a junior developer on your team."

Then make mistakes hard: in their SWE-bench agent, the model got confused by relative file paths once it had moved out of the root directory, so they changed the tool to only accept absolute paths, and the problem went away.

Anthropic's "Building effective agents" post (December 2024, Erik Schluntz and Barry Zhang) mostly argues for keeping things simple: start with a single LLM call, and add multi-step agent setups only when they measurably help.

The appendix goes into the less glamorous part, the tools an agent gets to use. A few points I didn't expect:
